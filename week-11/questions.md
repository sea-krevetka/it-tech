## 1. Зачем создавать пользовательскую сеть (bridge network) в Docker Compose, если есть дефолтная?

**Пользовательская сеть дает важные преимущества:**

### Преимущества пользовательской сети:

1. **DNS резолвинг** — сервисы доступны по имени контейнера, а не по IP-адресу
   ```yaml
   # В пользовательской сети работает:
   app:
     depends_on:
       - db
     environment:
       - DB_HOST=db  # Имя контейнера!
   ```

2. **Изоляция** — сервисы из разных compose-проектов не видят друг друга

3. **Лучшая производительность** — пользовательские bridge сети работают быстрее дефолтной

4. **Контроль над сетью** — можно задать подсеть, IP-диапазон, драйвер

## 2. В чем разница между `build` и `image` в описании сервиса?

### Директивы:

| Директива | Что делает | Когда использовать |
|-----------|------------|---------------------|
| **image** | Использует готовый образ из реестра | Для стандартных сервисов (Postgres, Redis, Nginx) |
| **build** | Собирает образ из Dockerfile | Для своего кода |

## 3. Что делает `depends_on`? Гарантирует ли он, что приложение в зависимом контейнере полностью инициализировалось?

### Что делает `depends_on`:
Определяет **порядок запуска** контейнеров. Docker сначала запускает зависимые контейнеры, только потом — основной.

### Не гарантирует:
- Что приложение в контейнере **завершило инициализацию**
- Что база данных **готова принимать запросы**
- Что порты **открыты**
- Что сервис **отвечает на healthcheck**

PostgreSQL запускается за 5-10 секунд, а приложение стартует сразу после создания контейнера — получим ошибку подключения.

## 4. Как работают healthcheck-и и как использовать их в `depends_on`?

### Что такое healthcheck:
Healthcheck — это команда, которую Docker выполняет периодически, чтобы проверить, жив ли контейнер.

### Структура healthcheck в docker-compose.yml:
```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
  interval: 30s      # Как часто запускать проверку
  timeout: 5s        # Максимальное время выполнения команды
  retries: 3         # Количество неудачных попыток до unhealthy
  start_period: 10s  # Время на инициализацию (проверки не выполняются)
```

### Типы команд:
```yaml
# Форма 1: CMD
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost/health"]

# Форма 2: CMD-SHELL
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres || exit 1"]

# Форма 3: NONE (отключить)
healthcheck:
  disable: true
```

### Состояния контейнера:
1. **starting** — начальный период (start_period)
2. **healthy** — проверка успешна 
3. **unhealthy** — проверка провалилась retries раз

## 5. Как передать переменные окружения в контейнер через Compose (минимум 2 способа)?

### Способ 1: Через `environment` (прямое указание)

```yaml
services:
  app:
    environment:
      - DB_HOST=postgres
      - DB_PORT=5432
      - APP_MODE=production
      - DEBUG=false
```

### Способ 2: Через `env_file` (файл с переменными)

```yaml
services:
  app:
    env_file:
      - .env              # базовый файл
      - .env.production   # переопределение (позже - выше приоритет)
```

**Файл .env:**
```env
DB_HOST=postgres
DB_PORT=5432
DB_PASSWORD=secret123
APP_MODE=development
```

### Способ 3: Из переменных окружения хоста

```yaml
services:
  app:
    environment:
      - SECRET_KEY=${SECRET_KEY}      # берется из окружения хоста
      - DATABASE_URL=${DATABASE_URL}
```

Запуск:
```bash
export SECRET_KEY="my-secret-key"
docker-compose up
```

### Способ 4: Через `.env` файл в корне проекта (для Compose)

**Файл .env в корне:**
```env
DB_PASSWORD=secret
APP_PORT=8080
REDIS_PASSWORD=redis_secret
```

**docker-compose.yml:**
```yaml
services:
  app:
    environment:
      - DB_PASSWORD=${DB_PASSWORD}
      - REDIS_PASSWORD=${REDIS_PASSWORD}
    ports:
      - "${APP_PORT}:8000"
```

### Приоритет переменных:
1. Переменные окружения хоста
2. Переменные в `environment`
3. Переменные в `env_file`
4. Переменные в `.env` файле Compose

## 6. Почему Docker Compose редко используют в продакшене (хотя это возможно)?

### Основные причины:

#### 1. **Отсутствие оркестрации**
- Нет автоматического перезапуска упавших контейнеров на других нодах
- Нет распределения нагрузки между несколькими серверами
- Нет self-healing (самовосстановления)

#### 2. **Масштабирование**
- `docker-compose up --scale` работает **только на одной ноде**
- Нет горизонтального масштабирования на кластер
- Нет автоматического scaling по метрикам (CPU, память)

#### 3. **Обновления без даунтайма**
- Rolling update не поддерживается
- Blue-green deployment нужно реализовывать вручную
- При обновлении сервис временно недоступен

#### 4. **Сетевая изоляция**
- Сложно настроить сложные сетевые политики
- Нет встроенного service discovery для нескольких нод
- Нет мTLS шифрования между сервисами

#### 5. **Безопасность**
- Нет встроенного менеджмента секретов
- Нет автоматического обновления сертификатов
- Нет RBAC (ролевой модели доступа)

#### 6. **Мониторинг и логирование**
- Нет встроенного сбора метрик
- Нет агрегации логов с нескольких нод
- Нет alerting (оповещений)
