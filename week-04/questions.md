### 1. Почему в микросервисах нельзя просто использовать `BEGIN TRANSACTION ... COMMIT` для операций, затрагивающих несколько сервисов?
В распределенной системе каждый микросервис имеет свою собственную базу данных, и эти базы данных физически разделены (находятся на разных серверах). 

Классические ACID-транзакции работают только в пределах одной базы данных, потому что они полагаются на:
- Общий менеджер транзакций
- Блокировки ресурсов
- Двухфазный коммит (2PC)

**Проблемы при попытке использовать распределенные транзакции (2PC):**
1. Производительность — сервисы блокируются на всё время транзакции
2. Надежность — если один сервис упадет во время коммита, данные могут быть потеряны
3. Масштабирование — синхронная связь между сервисами создает жесткие зависимости
4. CAP-теорема — в распределенных системх мы жертвуем согласованностью ради доступности

### 2. В чем разница между Оркестрацией и Хореографией? Какой подход проще для старта, а какой лучше масштабируется?

**Оркестрация (Orchestration):**
- Есть центральный управляющий (оркестратор), который говорит каждому сервису, что делать
- Все сервисы подчиняются оркестратору, узкое место для масштабирония 
- Проще для понимания

**Хореография (Choreography):**
- Нет центрального управляющего
- Сервисы общаются через события, легко масштабировать
- Сложнее отлаживать
- Каждый сервис сам решает, как реагировать на события
- Пример: сервис логов публикует событие "LogCreated", сервис хранилища ловит его и резервирует место

### 3. Что такое "компенсирующая транзакция"? Приведите пример.

Компенсирующая транзакция — это действие, которое отменяет (компенсирует) результаты предыдущей успешной транзакции в случае сбоя. Это аналог `ROLLBACK` в распределенных системах.

**Прямая транзакция (шаг 2 - резервирование места):**
```python
def step_reserve_storage(self, log_entry: LogEntry) -> bool:
    log_entry.data["storage_reserved"] = True
    log_entry.data["reserved_size"] = log_size
    log_entry.data["reserved_at"] = time.time()
    return True
```

**Компенсирующая транзакция (отмена резервирования):**
```python
def compensate_reserve_storage(self, log_entry: LogEntry):
    log_entry.data["storage_reserved"] = False
    log_entry.data.pop("reserved_size", None)
    log_entry.data.pop("reserved_at", None)
```


### 4. Может ли компенсирующая транзакция завершиться ошибкой? Что делать в таком случае?
Может, если: 
- Сеть недоступна
- Сервис, который должен выполнить компенсацию, упал
- Данные уже были изменены другим процессом

**Что делать:**

1. **Retry (повторные попытки)** — как в нашем коде:
2. **Dead Letter Queue (DLQ)** — если все попытки исчерпаны: 
3. **Ручное вмешательство** — администратор анализирует DLQ и исправляет вручную
4. **Журналирование** — полный аудит всех действий для восстановления


### 5. Что такое "согласованность в конечном счете" (Eventual Consistency)?

Согласованность в конечном счете — это модель согласованности, в которой система не гарантирует, что данные будут согласованы **немедленно**, но гарантирует, что **со временем** (при отсутствии новых изменений) все копии данных придут к согласованному состоянию.

Шаг 1: лог создан (NEW)
log_entry = orchestrator.create_log("log-001", data)
Шаг 2: резервирование места (еще не согласовано)
orchestrator.step_reserve_storage(log_entry)
# Шаг 3: обработка (DONE) - данные СОГЛАСОВАНЫ
orchestrator.step_process_log(log_entry)
