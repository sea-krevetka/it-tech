### 1. В чем разница между Continuous Integration, Continuous Delivery и Continuous Deployment?

**Continuous Integration (CI) — Непрерывная Интеграция**

Это практика, при которой разработчики часто (несколько раз в день) сливают свой код в общую ветку (например, main). Каждый такой пуш автоматически запускает сборку и тесты. Цель — как можно раньше обнаружить конфликты интеграции и сломанные тесты.

**Continuous Delivery (CD) — Непрерывная Доставка**

Это следующий шаг после CI. Если все тесты прошли успешно, система автоматически собирает Docker образ и разворачивает его на тестовом или стейджинг окружении. Решение о выкатке в продакшен принимает человек (нажатием кнопки). Таким образом, у вас всегда есть готовый к деплою артефакт.

**Continuous Deployment (CD) — Непрерывное Развертывание**

Это максимальная автоматизация. Каждый коммит, прошедший все тесты, автоматически попадает в продакшен без участия человека. Это требует очень высокого уровня доверия к тестам и мониторингу.


### 2. Почему тесты должны запускаться *до* сборки Docker образа (или хотя бы до его пуша)?

**Основная причина — экономия времени и ресурсов**

Сборка Docker образа — дорогая операция. Она включает в себя загрузку базового образа, копирование файлов, установку зависимостей. Если сборка занимает 5 минут, а тесты — 30 секунд, то при провале тестов после сборки вы теряете 5 минут впустую.

**Правильный порядок:**
1. Линтинг (быстро)
2. Тесты (быстро)
3. Сборка Docker образа (медленно)
4. Пуш в registry (медленно)


### 3. Зачем нужно кэширование зависимостей в CI пайплайне?

**Кэширование зависимостей нужно для ускорения сборки.** Без кэша каждый запуск CI будет скачивать все зависимости заново из интернета.

**Что происходит без кэширования:**

1. CI раннер запускается с чистого листа
2. Он скачивает pip/apt/npm пакеты из интернета (2-3 минуты)
3. Устанавливает их в виртуальное окружение (1 минута)
4. Запускает тесты
5. Всё повторяется при следующем запуске

**С кэшированием:**

1. CI раннер видит кэшированную папку с зависимостями
2. Проверяет, что файл requirements.txt не изменился
3. Если не изменился — просто использует кэш (секунды)
4. Если изменился — переустанавливает только новые зависимости

**Какие зависимости обычно кэшируют:**
- Pip (папка `~/.cache/pip`)
- Npm (папка `node_modules`)
- Docker слои (многоуровневое кэширование)
- Виртуальные окружения (`.venv`)


### 4. Что такое "Secret" в контексте CI/CD? Как безопасно передать пароль от Docker Hub в пайплайн?

**Secret** — это зашифрованная переменная окружения, которая хранится отдельно от кода и не видна в логах CI. В неё помещают пароли, API ключи, токены доступа к registry и другие конфиденциальные данные.

**Почему секреты нельзя хранить в коде:**

- Код может попасть в публичный репозиторий
- Даже в приватном репозитории доступ есть у многих разработчиков
- Хардкод пароля делает ротацию пароля невозможной без изменения кода

**Как безопасно передать пароль от Docker Hub в GitHub Actions:**

1. **Зашифровать пароль через интерфейс CI:**
   - GitHub Actions: Settings → Secrets and variables → Actions → New repository secret
   - GitLab CI: Settings → CI/CD → Variables

2. **Использовать готовые actions для логина:**
   ```yaml
   - name: Login to Docker Hub
     uses: docker/login-action@v2
     with:
       username: ${{ secrets.DOCKER_USERNAME }}
       password: ${{ secrets.DOCKER_PASSWORD }}
   ```

3. **Или через docker login команду:**
   ```yaml
   - name: Docker login
     run: echo "${{ secrets.DOCKER_PASSWORD }}" | docker login -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin
   ```



### 5. Что такое "Matrix Build" (матричная сборка)?

**Matrix Build** — это возможность запускать один и тот же пайплайн с разными параметрами параллельно. Это похоже на таблицу (матрицу), где строки и столбцы — разные комбинации значений.

**Когда используется матричная сборка:**

- Тестирование с разными версиями языка (Python 3.9/3.10/3.11)
- Тестирование на разных ОС (Linux, Windows, Mac)
- Тестирование с разными версиями зависимостей (Django 3.x, 4.x)
- Сборка для разных архитектур (amd64, arm64)
- Тестирование с разными конфигурациями (режим debug/release)


### 6. Почему нельзя хранить конфиги продуктовой среды в репозитории кода (или можно, но осторожно)?

**Почему нельзя (основные причины):**

1. **Безопасность** — конфиги продакшена содержат секреты: пароли от БД, API ключи, приватные сертификаты, токены доступа. Хранение их в репозитории — это как повесить ключи от сейфа на видное место.

2. **Разные окружения требуют разных конфигов** — у вас есть dev, stage, prod. У каждого свои пароли, свои адреса баз данных, свои домены. Нельзя их смешивать в одном файле.

3. **Ротация секретов невозможна** — если секрет скоммичен в репозиторий, его остаётся только менять. Но Git хранит историю, и старый пароль всё равно остаётся доступен.

4. **Кто имеет доступ к репозиторию, получает доступ к продакшену** — это нарушает принцип минимальных привилегий.

**Как правильно хранить конфиги:**

1. **Шаблоны конфигов** — хранить в репозитории файлы-примеры (например, `config.yaml.example` или `.env.example`) с фейковыми значениями.

2. **Через CI/CD переменные** — настоящие значения передавать через переменные окружения (secrets) в момент деплоя.

3. **External Secret Management** — использовать внешние системы (HashiCorp Vault, AWS Secrets Manager, Doppler) для хранения секретов.

4. **Helm** — хранить разные values-файлы для разных окружений вне основного репозитория или в зашифрованном виде (например, с помощью `sops`).

**Когда можно но осторожно:**

- Если репозиторий полностью приватный
- Если доступ к репозиторию строго ограничен
- Если конфиг общий для всех окружений (например, настройки логирования)
- Если вы используете шифрование файлов (git-crypt, sops) и ключи для расшифровки хранятся отдельно
