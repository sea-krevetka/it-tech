### 1. Что такое OWASP Top 10? Назовите 3 любые уязвимости оттуда.

**OWASP Top 10** — это стандартный документ осведомленности о безопасности, который представляет собой список 10 наиболее критических рисков безопасности для веб-приложений. Составляется организацией Open Web Application Security Project (OWASP) на основе статистики уязвимостей из реальных проектов.

**Три уязвимости из OWASP Top 10:**

1. **Broken Access Control (Нарушение контроля доступа)**
   - Пользователь может видеть или изменять данные других пользователей
   - Например: смена ID в URL (`/user/123` → `/user/124`) дает доступ к чужому профилю

2. **Injection (Инъекции)**
   - Внедрение вредоносного кода в запросы к интерпретатору
   - Например: SQL Injection (`' OR '1'='1`), Command Injection, NoSQL Injection

3. **Cryptographic Failures (Криптографические ошибки)**
   - Хранение паролей в открытом виде
   - Использование слабых алгоритмов шифрования (MD5, SHA1)
   - Передача данных по незащищенному каналу (HTTP вместо HTTPS)

### 2. Чем Аутентификация отличается от Авторизации?

| Характеристика | Аутентификация | Авторизация |
|----------------|----------------|-------------|
| **Что это** | Проверка "кто ты?" | Проверка "что тебе разрешено?" |
| **Когда происходит** | Первой | После аутентификации |
| **Как проверяет** | Пароль, токен, биометрия | Роли, права, разрешения |
| **Пример** | Вход по логину/паролю | Доступ к админ-панели только у администраторов |
| **Ошибка** | "401 Unauthorized" (неверные учетные данные) | "403 Forbidden" (недостаточно прав) |

**Простая аналогия:**
- **Аутентификация** — предъявление паспорта на входе в здание
- **Авторизация** — проверка, есть ли у вас пропуск в конкретный кабинет

### 3. Что такое SQL Injection и как ORM помогают от неё защититься?

**SQL Injection** — тип атаки, при котором злоумышленник внедряет вредоносный SQL-код в запрос через неэкранированные пользовательские данные.

**Пример уязвимого кода:**
```python
# Плохо: прямая подстановка
user_id = request.GET['id']
query = f"SELECT * FROM users WHERE id = {user_id}"
cursor.execute(query)

# Атака: user_id = "1 OR 1=1"
# Результат: SELECT * FROM users WHERE id = 1 OR 1=1  # вернет ВСЕХ пользователей!
```

**Как ORM защищают от SQL Injection:**

1. **Параметризация запросов**
   ```python
   user = User.objects.filter(id=user_id)
   ```

2. **Экранирование специальных символов**
   - ORM автоматически экранирует кавычки, точки с запятой и другие опасные символы

3. **Разделение кода и данных**
   - SQL структура запроса фиксирована, пользовательские данные передаются как параметры

4. **Типизация полей**
   - ORM проверяет типы данных (число не может быть строкой)

### 4. Почему нельзя хранить секреты (API ключи, пароли БД) в коде репозитория?

**Основные причины:**

1. **Код попадает в Git историю**
   - Секреты остаются в истории даже после удаления
   - Злоумышленник может найти старые коммиты с секретами

2. **Доступ к репозиторию = доступ ко всем секретам**
   - Любой разработчик с доступом к коду видит секреты
   - Если репозиторий публичный — секреты видны всем

3. **Разные окружения требуют разных секретов**
   - Dev, staging, production — у каждого свои ключи
   - Нельзя хранить production ключи в коде

4. **Ротация секретов становится невозможной**
   - При смене ключа нужно менять код и пересобирать приложение

### 5. Что такое "Man-in-the-Middle" (MitM) атака и как HTTPS защищает от неё?

**Man-in-the-Middle (MitM) атака** — это атака, при которой злоумышленник тайно перехватывает и, возможно, изменяет коммуникацию между двумя сторонами, которые считают, что общаются напрямую.

**Как выглядит MitM:**
```
Клиент -> Злоумышленник -> Сервер
Клиент <- Злоумышленник <- Сервер
```
Злоумышленник читает, записывает и может изменять все данные.

**Примеры MitM:**
- Подключение к незащищенному WiFi в кафе (злоумышленник создает фальшивую точку доступа)
- ARP poisoning в локальной сети
- Вредоносный прокси или роутер

**Как HTTPS защищает от MitM:**

1. **Шифрование**
   - Все данные между клиентом и сервером шифруются
   - Злоумышленник видит только бессмысленный набор байтов

2. **Аутентификация сервера (SSL/TLS сертификаты)**
   - Браузер проверяет, что сервер — это тот, за кого он себя выдает
   - Сертификат подписан доверенным центром сертификации (CA)

3. **Целостность данных**
   - Подпись каждого сообщения
   - Если злоумышленник изменит данные, подпись станет невалидной

### 6. Зачем нужен принцип "минимальных привилегий" (Least Privilege)?

**Принцип минимальных привилегий (Least Privilege)** — это практика безопасности, при которой пользователь, процесс или система получают только те права доступа, которые абсолютно необходимы для выполнения их функций, и не более того.

**Зачем нужен:**

1. **Ограничение ущерба при взломе**
   - Если взломали сервис, который имеет доступ только к своей БД — ущерб минимален
   - Если сервис работает от root — взломан весь сервер

2. **Предотвращение случайных ошибок**
   - Пользователь с правами на чтение случайно не удалит данные

3. **Упрощение аудита**
   - Меньше прав = меньше мест, которые нужно проверять

4. **Соответствие регуляторам (GDPR, PCI DSS, SOC2)**
   - Многие стандарты требуют Least Privilege
