### 1. Что такое слой в Docker и почему порядок команд в Dockerfile важен для кэширования?

**Слой** — это результат выполнения инструкции в Dockerfile (FROM, RUN, COPY, ADD). Каждая инструкция создает новый слой, который кэшируется Docker'ом.

**Почему важен порядок:**
- Docker сравнивает хэш инструкции и файлов, участвующих в ней
- Если инструкция не изменилась, Docker использует кэшированный слой
- **Часто меняющиеся инструкции должны идти внизу**, а редко меняющиеся — вверху

**Правильный порядок:**
```dockerfile
FROM python:3.11          # Редко меняется
COPY requirements.txt .   # Меняется редко (только при обновлении зависимостей)
RUN pip install -r requirements.txt  # Кэшируется, если requirements.txt не изменился
COPY . .                  # Меняется часто — последний слой
```

**Неправильный порядок:**
```dockerfile
COPY . .                  # Меняется часто — сбросит кэш всех следующих слоев
RUN pip install -r requirements.txt  # Будет переустанавливаться при каждом изменении кода!
```

### 2. В чем суть Multi-stage build? Какие проблемы он решает?

**Суть:** Использование нескольких этапов (FROM) в одном Dockerfile. На первом этапе устанавливаются зависимости и компилируется код, на финальный этап копируется только нужный результат.

**Проблемы, которые решает:**

1. **Большой размер образа**
   - Без multi-stage: образ содержит компиляторы, исходники библиотек, кэш pip → 1-2 GB
   - С multi-stage: только исполняемый код и runtime зависимости → 50-200 MB

2. **Безопасность**
   - В финальном образе нет компиляторов и инструментов сборки
   - Меньше поверхность для атак

3. **Время сборки**
   - Кэширование слоев между этапами
   - Можно использовать разные базовые образы для разных этапов

### 3. Зачем нужен файл `.dockerignore`?

**Файл `.dockerignore`** исключает файлы и директории из контекста сборки, который отправляется Docker демону при выполнении `docker build`.

**Зачем нужен:**

1. **Уменьшение контекста сборки**
   - Не отправлять на сервер виртуальные окружения (`.venv/` → 100+ MB)
   - Не отправлять Git историю (`.git/` → десятки MB)

2. **Ускорение сборки**
   - Меньше данных для передачи
   - Быстрее начинается сборка

3. **Безопасность**
   - Не попадут в образ секреты (`.env`, ключи, пароли)
   - Не попадут локальные конфиги

4. **Предотвращение конфликтов**
   - Локальные виртуальные окружения не будут скопированы в контейнер

### 4. Чем отличаются инструкции `CMD` и `ENTRYPOINT`?

| Характеристика | CMD | ENTRYPOINT |
|----------------|-----|------------|
| **Назначение** | Значения по умолчанию для команды | Основная команда контейнера |
| **Переопределение** | Легко переопределяется через `docker run` | Сложнее переопределить (требуется `--entrypoint`) |
| **Использование** | `CMD ["python", "app.py"]` | `ENTRYPOINT ["python"]` |

**Комбинации:**

1. **Только CMD** — можно переопределить полностью
   ```dockerfile
   CMD ["python", "app.py"]
   ```
   ```bash
   docker run image python other.py  # переопределено
   ```

2. **Только ENTRYPOINT** — нельзя переопределить
   ```dockerfile
   ENTRYPOINT ["python", "app.py"]
   ```
   ```bash
   docker run image other.py  # аргументы добавятся, но python app.py останется
   ```

3. **ENTRYPOINT + CMD** — гибкий подход
   ```dockerfile
   ENTRYPOINT ["python"]
   CMD ["app.py"]
   ```
   - По умолчанию: `python app.py`
   - Можно переопределить: `docker run image other.py` → `python other.py`

### 5. Почему рекомендуется использовать `COPY` вместо `ADD`?

| Характеристика | COPY | ADD |
|----------------|------|-----|
| **Что делает** | Копирует файлы из контекста сборки | Копирует + расширенные возможности |
| **Распаковка архивов** | Нет | Да (автоматически распаковывает .tar) |
| **URL загрузка** | Нет | Да (может скачать по URL) |
| **Предсказуемость** | Высокая | Низкая (неожиданное поведение) |

**Почему COPY лучше:**

1. **Прозрачность** — COPY делает только одно действие: копирует файлы
2. **Безопасность** — ADD может скачать вредоносный файл по URL
3. **Кэширование** — URL в ADD может измениться без изменения Dockerfile
4. **Размер** — распаковка архивов может привести к неожиданному увеличению размера

**Когда использовать ADD:**
- Только когда нужно распаковать локальный .tar архив
- В остальных случаях — всегда COPY

### 6. Почему приложение в контейнере должно слушать `0.0.0.0`, а не `127.0.0.1`?

**Причина:** Контейнер имеет свою собственную сетевую изоляцию.

| Адрес | Назначение | Доступ с хоста |
|-------|------------|----------------|
| `127.0.0.1` (localhost) | Только внутри контейнера | Нет |
| `0.0.0.0` | Все сетевые интерфейсы | Да |

**Объяснение:**

1. **Сетевые интерфейсы контейнера:**
   - `lo` (loopback) — `127.0.0.1` — только внутри контейнера
   - `eth0` — виртуальный сетевой интерфейс — связан с хостом

2. **При слушании на `127.0.0.1`:**
   ```python
   # Приложение внутри контейнера
   uvicorn.run(app, host="127.0.0.1", port=8000)
   ```
   - Приложение доступно только изнутри контейнера
   - `docker run -p 8000:8000` НЕ сработает — порт не пробросится

3. **При слушании на `0.0.0.0`:**
   ```python
   # Правильно
   uvicorn.run(app, host="0.0.0.0", port=8000)
   ```
   - Приложение доступно на всех интерфейсах
   - `docker run -p 8000:8000` работает — запросы с хоста попадают в контейнер
