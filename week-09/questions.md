### 1. Зачем нужен Signaling сервер, если WebRTC — это P2P технология?

**Signaling сервер нужен для "знакомства" браузеров.** WebRTC — это P2P технология, но перед тем как установить прямое соединение, браузеры должны:

- **Обменяться технической информацией** (SDP) — какие кодеки поддерживают, какие форматы видео/аудио
- **Обменяться сетевыми адресами** (ICE candidates) — как до них можно достучаться
- **Согласовать параметры соединения**

Проблема в том, что браузеры изначально **не знают друг о друге**. Им нужен посредник, который их познакомит. Signaling сервер выполняет роль этой "доски объявлений".

**После установки P2P соединения** Signaling сервер больше не нужен — данные идут напрямую.


### 2. Что такое NAT и почему он мешает прямому соединению?

**NAT (Network Address Translation)** — это механизм, который позволяет нескольким устройствам в локальной сети использовать один общий внешний IP-адрес.

**Как это работает:**
- Ваш роутер имеет один внешний IP (например, `85.123.45.67`)
- Ваш компьютер имеет локальный IP (например, `192.168.1.100`)
- Когда вы выходите в интернет, роутер подменяет ваш локальный IP на свой внешний и запоминает, какому устройству какой ответ отдать

**Почему NAT мешает прямому соединению:**

1. **Устройства за NAT не имеют своего внешнего IP** — они знают только свой локальный адрес, который бесполезен в интернете
2. **Внешний адрес общий** — чтобы соединиться с конкретным устройством, нужно знать, какой порт ему соответствует
3. **NAT блокирует входящие соединения** — если никто не стучался снаружи, NAT не знает, куда направить пакет

**Пример:**
```
Компьютер А (за NAT) хочет соединиться с Компьютером Б (за NAT)
Проблема: ни один из них не знает, как "достучаться" до другого
```


### 3. В чем разница между STUN и TURN серверами?

| Характеристика | STUN | TURN |
|----------------|------|------|
| **Что делает** | Помогает узнать свой внешний IP и порт | Ретранслирует весь трафик через себя |
| **Участие в передаче данных** | Только в начале (для "пробивания" NAT) | Всё время соединения |
| **Загрузка сервера** | Минимальная | Максимальная (весь трафик через него) |
| **Задержка** | Только в начале | Добавляет задержку |
| **Когда используется** | Когда NAT можно "пробить" | Когда STUN не сработал (strict NAT) |
| **Стоимость** | Дешево (почти бесплатно) | Дорого (пропуск трафика) |

**Процесс:**
1. Сначала пробуем STUN — клиент узнает свой внешний адрес
2. Пытаемся установить прямое P2P соединение
3. Если не получается — используем TURN как fallback

**Пример TURN сервера:** Если оба устройства в корпоративной сети с очень строгим NAT, прямое соединение невозможно — трафик идет через TURN.

### 4. Что такое ICE Candidate?

**ICE Candidate** — это потенциальный адрес (IP + порт), по которому можно достучаться до устройства.

**Типы кандидатов (от приоритетных к менее приоритетным):**

1. **Host candidate** — локальный IP устройства (например, `192.168.1.100:54321`)
2. **Server Reflexive candidate** — внешний IP, полученный через STUN сервер (например, `85.123.45.67:12345`)
3. **Relay candidate** — адрес TURN сервера (запасной вариант)

**Процесс сбора кандидатов (ICE gathering):**
```
Браузер собирает все возможные кандидаты:
- "Я думаю, меня можно найти по адресу 192.168.1.100:54321"
- "STUN сказал, что меня видно как 85.123.45.67:12345"
- "Если ничего не сработает, используй TURN server: turn.example.com:3478"
```

**Зачем это нужно:** Устройства обмениваются этими кандидатами через Signaling сервер, а затем пробуют соединиться (ICE connectivity checks) — первый успешный кандидат используется.

### 5. Почему WebRTC обычно использует UDP, а не TCP?

| Характеристика | UDP | TCP |
|----------------|-----|-----|
| **Задержка** | Низкая | Выше (из-за подтверждений) |
| **Потеря пакетов** | Не страшно (можно восстановить кодеком) | Критично (ждет повторной отправки) |
| **Передача вне порядка** | Да | Нет |
| **Гарантия доставки** | Нет | Есть |
| **Head-of-line blocking** | Нет | Есть |

**Основные причины выбора UDP:**

1. **Низкая задержка** — в реальном времени (видеозвонок, игра) задержка важнее идеального качества
2. **Не критично потерять пакет** — потеря одного кадра видео или пары миллисекунд звука незаметна
3. **Нет Head-of-line blocking** — потерянный пакет не блокирует остальные
4. **Возможность исправить ошибки на уровне приложения** — WebRTC сам восстанавливает потерянные пакеты

**Когда TCP может быть лучше:**
- Передача файлов (важна гарантия доставки)
- Чат (можно использовать Data Channel с конфигурацией `{ordered: true}`)

### 6. Что такое SDP (Session Description Protocol) и какая информация в нем содержится?

**SDP (Session Description Protocol)** — это текстовый формат для описания параметров мультимедийной сессии. В WebRTC используется для "переговоров" между браузерами.

**Что содержится в SDP:**

1. **Медиа-информация:**
   - Типы медиа (аудио, видео, data channel)
   - Кодеки (VP8, H.264, Opus и т.д.)
   - Форматы и параметры кодеков

2. **Сетевая информация:**
   - IP-адреса (кандидаты)
   - Порты для медиа-потоков
   - Протоколы (UDP/TCP)

3. **Управление сессией:**
   - Идентификатор сессии
   - Версия (при изменении параметров)
   - Направление потока (sendrecv, sendonly, recvonly)

**Пример SDP:**
```
v=0
o=- 123456 1 IN IP4 192.168.1.100
s=-
t=0 0
a=group:BUNDLE 0
m=audio 54321 UDP/TLS/RTP/SAVPF 111 103
c=IN IP4 192.168.1.100
a=rtpmap:111 opus/48000/2
a=sendrecv
m=video 54322 UDP/TLS/RTP/SAVPF 96
c=IN IP4 192.168.1.100
a=rtpmap:96 VP8/90000
```

**Как используется в WebRTC:**
1. Сторона А создает SDP (offer) и отправляет через Signaling
2. Сторона Б получает offer, создает SDP (answer) и отправляет обратно
3. Браузеры на основе SDP настраивают кодеки и медиа-потоки

**SDP не определяет само соединение** (это делают ICE кандидаты), но описывает **как** должно выглядеть соединение после его установки.
