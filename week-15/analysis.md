## Сравнение REST vs gRPC

| Метрика | REST | gRPC | Преимущество |
|---------|------|------|--------------|
| **Макс. RPS (P95 < 100ms)** | ~320 | ~850 | gRPC (2.7x) |
| **Макс. RPS (P99 < 200ms)** | ~450 | ~1100 | gRPC (2.4x) |
| **Latency при 100 RPS** | 28.5 ms | 18.2 ms | gRPC (1.6x) |
| **Latency при 500 RPS** | 512 ms | 212 ms | gRPC (2.4x) |
| **Точка насыщения** | ~450 RPS | ~1100 RPS | gRPC |


### 1. Точка насыщения

- **REST сервер**: достигает насыщения при ~450 RPS. После этого RPS практически не растет, а Latency резко увеличивается.
- **gRPC сервер**: достигает насыщения при ~1100 RPS. У gRPC точка насыщения выше из-за эффективной сериализации и HTTP/2.

### 2. Зависимость Latency от RPS

- **В зоне нормы (до насыщения)**: Latency растет линейно с увеличением RPS.
- **В зоне насыщения**: Latency начинает расти экспоненциально из-за:
  - Очередей в сетевом стеке
  - Соревнования за CPU/память
  - Увеличения времени GC (для Python)

### 3. Почему gRPC быстрее?

- **Бинарный протокол**: Protobuf сериализует данные в компактный бинарный вид (меньше данных для передачи)
- **HTTP/2 мультиплексирование**: Одно TCP соединение для всех запросов
- **Эффективная сериализация**: Меньше нагружает CPU при парсинге

### 4. Проблемы, выявленные в ходе тестирования

1. **Python GIL ограничивает максимальный RPS**: Оба сервиса на Python показывают насыщение раньше, чем сервисы на Go/Java
2. **REST сериализация JSON**: Составляет ~30% времени обработки запроса
3. **При высоком RPS (500+)**: Начинаются ошибки таймаутов и 5xx ответы


1. **gRPC показывает лучшую производительность** во всех сценариях (в 2-3 раза выше RPS при тех же задержках)
2. **Точка насыщения для REST** ~450 RPS, для gRPC ~1100 RPS
3. **Для production с нагрузкой >500 RPS** рекомендуется использовать gRPC с 2-3 репликами
4. **При нагрузке <100 RPS** разница между REST и gRPC незначительна (можно выбрать любой)
