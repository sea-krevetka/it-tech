### 1. Почему мы создаем Deployment, а не сразу Pod?

Pod'ы в Kubernetes не перезапускаются, если они умирают. Pod — это "смертная" единица. Deployment же предоставляет декларативное управление Pod'ами.

### 2. В чем разница между Liveness и Readiness пробами? Что произойдет, если провалится каждая из них?

| Характеристика | Liveness Probe | Readiness Probe |
|----------------|----------------|-----------------|
| **Назначение** | Проверяет, жив ли контейнер | Проверяет, готов ли контейнер принимать трафик |
| **Что проверяет** | Не зависло ли приложение | Загрузилось ли приложение полностью |
| **При провале** | Перезапускает контейнер (kubelet убивает и создает новый) | Убирает Pod из Service (не направляет трафик) |
| **Когда запускается** | Сразу после старта | После успешной старта (с учетом `initialDelaySeconds`) |
| **Пример** | Проверка `/health` каждые 30 сек | Проверка `/ready` после загрузки данных |

**Что происходит при провале:**

- **Liveness провалилась**: Kubernetes перезапускает контейнер (попытка оживить)
- **Readiness провалилась**: Pod удаляется из эндпоинтов Service, трафик не идет, но Pod продолжает работать (пытается стать здоровым)


### 3. Что такое "requests" и "limits" для CPU и памяти? Почему важно их указывать?

**Requests (запросы):**
- Минимальное количество ресурсов, которое Kubernetes гарантирует контейнеру
- Используется для **планирования** (scheduling) Pod'а на ноду
- Пример: `memory: "256Mi"` — гарантировано 256 МБ памяти

**Limits (ограничения):**
- Максимальное количество ресурсов, которое может использовать контейнер
- Используется для **ограничения** (изоляции) контейнера
- Пример: `memory: "512Mi"` — контейнер не может использовать больше 512 МБ

**Почему важно указывать:**

1. **Без requests:**
   ```yaml
   # Проблема: один "жадный" под может съесть всю память ноды
   # Ядро Linux начнет убивать процессы (OOM Kill)
   ```

2. **Без limits:**
   ```yaml
   # Проблема: контейнер может использовать все ресурсы ноды
   # Остальные поды "голодают"
   ```


### 4. Как Service находит свои Pod-ы? (Подсказка: Labels & Selectors)

**Service использует механизм Labels и Selectors.**

**Как это работает:**

1. **Поды имеют метки (labels):**
   ```yaml
   # Pod (внутри Deployment)
   template:
     metadata:
       labels:
         app: items-app
         tier: backend
         version: v1
   ```

2. **Service использует селектор (selector) для поиска Pod'ов:**
   ```yaml
   # Service
   spec:
     selector:
       app: items-app      # Находит все Pod'ы с label app=items-app
       tier: backend
     ports:
     - port: 80
       targetPort: 8181
   ```

3. **Процесс:**
   - Service создает объект Endpoints, содержащий IP-адреса всех Pod'ов, соответствующих селектору
   - Когда Pod'ы добавляются/удаляются, Endpoints обновляются автоматически
   - Трафик, приходящий на Service, балансируется между этими Pod'ами


### 5. Какой тип сервиса (ClusterIP, NodePort, LoadBalancer) используется для внутреннего общения, а какой — для внешнего доступа?

| Тип Service | Доступ | Use Case |
|-------------|--------|----------|
| **ClusterIP** | Только внутри кластера | **Внутреннее общение** между микросервисами |
| **NodePort** | Снаружи кластера (через IP ноды : порт) | Тестирование, доступ без LoadBalancer |
| **LoadBalancer** | Снаружи кластера (через внешний LB) | **Внешний доступ** в production |
| **ExternalName** | Прокси на внешний DNS | Доступ к внешним сервисам |

### 6. Что такое "Rolling Update" в контексте Деплоймента?

**Rolling Update** — стратегия обновления Pod'ов в Deployment, при которой старые версии заменяются новыми постепенно, без простоя сервиса.

**Как работает:**

1. Создаются новые Pod'ы с новой версией
2. Когда новые Pod'ы становятся готовыми (readinessProbe успешна), старые Pod'ы удаляются
3. Процесс повторяется, пока все Pod'ы не будут обновлены
