### 1. Что такое Server Streaming? Приведите пример использования.

**Server Streaming** — это тип взаимодействия в gRPC, при котором клиент отправляет один запрос, а сервер отвечает потоком сообщений.

**Пример использования:**
- **Отслеживание статуса посылки** — клиент запрашивает статус отправки, сервер стримит обновления
- **Ленты новостей** — клиент запрашивает посты, сервер отправляет их порциями
- **Биржевые котировки** — клиент подписывается на котировки, сервер шлет изменения
- **Логи** — клиент запрашивает логи, сервер стримит их в реальном времени

---

### 2. Чем Server Streaming отличается от просто получения большого списка (List) в одном ответе?

| Характеристика | Server Streaming | List (один ответ) |
|----------------|-----------------|-------------------|
| **Время до первого байта** | Мгновенно (сразу получаем первые данные) | Нужно ждать полного сбора |
| **Использование памяти** | Низкое (данные обрабатываются по мере получения) | Высокое (весь список в памяти) |
| **Real-time обновления** | Поддерживает (новые данные можно отправлять динамически) | Не поддерживает |
| **Объем данных** | Неограниченный (бесконечный поток) | Ограничен размером сообщения |
| **Обработка ошибок** | Сложнее (может прерваться в середине) | Проще (успех/ошибка целиком) |
| **Использование сети** | Открытое соединение на длительное время | Короткое соединение |

### 3. Какие метрики производительности существуют (Latency, Throughput, CPU Usage)?

**Основные метрики:**

1. **Latency (Задержка)**
   - Среднее время ответа (Average)
   - P95, P99 процентили
   - Время до первого байта (TTFB)

2. **Throughput (Пропускная способность)**
   - RPS (Requests Per Second) — запросов в секунду
   - Данных в секунду (MB/s)
   - Количество одновременно обрабатываемых соединений

3. **CPU Usage (Использование CPU)**
   - Процент загрузки процессора
   - Время системных вызовов
   - Эффективность сериализации

4. **Memory Usage (Использование памяти)**
   - RSS (Resident Set Size)
   - Утечки памяти
   - Аллокации на запрос

5. **Network I/O**
   - Переданные байты
   - Количество пакетов
   - TCP retransmits

### 4. Почему важно переиспользовать канал (Channel) в gRPC клиенте при замерах производительности?

**Потому что создание нового канала — дорогая операция:**

1. **TCP handshake (3-way handshake)** — установление соединения занимает время (RTT)
2. **HTTP/2 соединение** — требует настройки потоков, окон
3. **TLS рукопожатие** — если используется шифрование (еще один RTT)
4. **Выделение ресурсов** — память под буферы, потоки

При замерах производительности мы хотим измерить **скорость самого RPC**, а не накладные расходы на установку соединений.

### 5. В каких сценариях REST может оказаться быстрее или удобнее gRPC?

**REST может быть быстрее gRPC, когда:**

1. **Очень маленькие запросы** — накладные расходы на бинарную сериализацию могут перевешивать
2. **Кэширование критично** — HTTP кэш (CDN, браузер) может дать огромный выигрыш
3. **Данные уже в текстовом формате** — перекодировка в бинарный добавляет лишнюю работу

**REST удобнее gRPC, когда:**

1. **Публичное API** — разработчикам проще отлаживать через curl/браузер
2. **Браузерные клиенты** — gRPC-web все еще имеет ограничения
3. **Простая структура данных** — JSON легко читать и изменять
4. **Быстрый прототип** — не нужно описывать .proto и генерировать код
5. **Несколько языков** — JSON поддерживается везде "из коробки"

### 6. Что такое "Head-of-Line Blocking" и как HTTP/2 (и gRPC) решает эту проблему?

**Head-of-Line Blocking (HOL Blocking)** — проблема, когда один медленный запрос блокирует все остальные в очереди.

**В HTTP/1.1:**
- Одно TCP соединение = одна очередь
- Запросы выполняются последовательно
- Если первый запрос загружает большой файл, остальные ждут


**В HTTP/2:**
- Одно TCP соединение = несколько параллельных потоков (streams)
- Каждый поток независим
- Потоки мультиплексируются внутри одного соединения

**Как HTTP/2 решает проблему:**

1. **Мультиплексирование** — несколько потоков в одном соединении
2. **Фреймы** — данные разбиваются на маленькие фреймы, которые могут перемежаться
3. **Приоритизация** — можно указать важность потока
4. **Server Push** — сервер может отправлять данные до запроса

**Пример:** 
- REST (HTTP/1.1): загружаете страницу → 10 запросов к разным ресурсам → ждете в очереди
- gRPC (HTTP/2): те же 10 запросов → параллельно → загрузка быстрее

**Преимущества gRPC из-за HTTP/2:**
- Высокая пропускная способность при множестве запросов
- Низкая задержка для быстрых запросов даже при наличии медленных
- Эффективное использование TCP соединений
