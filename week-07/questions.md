### 1. Зачем нужен файл `.proto`? Почему мы не пишем классы сообщений сразу на Python?

Файл `.proto` (Protocol Buffers IDL) позволяет:
- Определить контракт независимо от языка — один `.proto` файл можно использовать для генерации кода на Python, Go, Java, C++ и других языках
- Обеспечить строгую типизацию — поля имеют фиксированные типы (int32, string, bool и т.д.)
- Автоматизировать сериализацию/десериализацию — не нужно писать вручную код для упаковки данных в бинарный формат
- Гарантировать совместимость — номера полей (тэги) обеспечивают обратную совместимость

Если сразу на Python:
- Нельзя использовать код на других языках
- Вручную реализовывать сериализацию
- Сложнее поддерживать обратную совместимость

### 2. Что такое Unary RPC? Чем он концептуально похож на REST запрос?

Unary RPC — простейший тип взаимодействия в gRPC, при котором:
- Клиент отправляет **один** запрос
- Сервер возвращает **один** ответ
- Вызов блокируется до получения ответа

Сходство с REST запросом:
- Оба работают по принципу "запрос-ответ" (request-response)
- Оба синхронные по своей природе
- Оба могут быть использованы для CRUD операций
- В обоих клиент ждет ответа от сервера

Отличие от REST:
- Unary RPC использует бинарный протокол (Protobuf), REST — текстовый (JSON/XML)
- Unary RPC имеет строгий контракт, определенный в `.proto` файле

### 3. Почему gRPC обычно эффективнее REST (JSON) по процессору и трафику?

По трафику:
- Бинарный формат — Protobuf сериализует данные в компактный бинарный вид, JSON — в текстовый
- Меньше служебной информаци* — нет повторяющихся ключей полей, используются тэги

По процессору:
- Типизированные данные — не нужно преобразовывать строки в числа и обратно
- Отсутствие парсинга текста — JSON требует сложного текстового парсинга


### 4. Что такое "обратная совместимость" в Protobuf и зачем нужны номера полей (тэги, например `= 1`)?

Обратная совместимость — это способность старой версии программы читать данные, созданные новой версией, и наоборот.

Номера полей (тэги) обеспечивают обратную совместимость, тк:

1. Идентифицируюи по номеру, а не по имени. Протокол использует номер поля (тэг) для идентификации, а не его имя. Тогда можно:
   - Добавить новое поле с новым тэгом — старый клиент его проигнорирует
   - Удалить поле — старый клиент перестанет его использовать
   - Переименовать поле — номер останется тем же, данные будут читаться корректно

2. Нельзя менять тип поля — изменение типа нарушает совместимость
3. Нельзя переназначать номера — тэги фиксированы и не могут быть изменены

### 5. Что такое Stub (стаб) на клиенте и Servicer на сервере?

Stub на клиенте:
- Сгенерированный код, который клиент использует для вызова методов сервера
- Выглядит как обычный локальный объект с методами
- Скрывает всю сложность сетевого взаимодействия (сериализация, отправка, прием, десериализ.)

Servicer на сервере:
- Это класс реализованный на сервере
- Наследуется от сгенерированного базового класса
- Реализует все методы, объявленные в `.proto` файле

### 6. В каких случаях вы бы выбрали REST, а в каких — gRPC?

REST:

1. Публичное API — REST понятен разработчикам, легко тестировать через браузер
2. Кэширование на уровне HTTP — нужно кэширование на CDN или прокси
3. Простота и гибкость — не нужна строгая типизация
5. CRUD операции — простые операции над ресурсами
6. JSON уже используется — система уже построена на JSON

gRPC:

1. Внутренние микросервисы — высокая производительность критична
2. Низкая задержка и высокая пропускная способность — нужно быстро обрабатывать много запросов
3. Полиглотная среда — сервисы на разных языках должны общаться
4. Строгие контракты — нужна гарантия типов и обратной совместимости
5. Streaming — нужна двунаправленная передача данных
